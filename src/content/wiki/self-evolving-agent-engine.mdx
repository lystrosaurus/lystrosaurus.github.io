## 项目定位

让 AI 自动理解大型 Java 项目的业务逻辑，输出结构化知识卡片。

| 维度 | 说明 |
|------|------|
| 输入 | Java 源码 + MySQL 数据库 |
| 输出 | Markdown 知识卡片（API 职责、业务规则、数据库操作、代码质量） |
| 核心挑战 | 代码分层混乱、注释不可信、1000+ API、业务逻辑分散在 Service/Mapper/DAO |

## 关键决策：零外部 API 依赖

不依赖 Anthropic/OpenAI API，原因：

1. 分析 1000+ API，调用成本高且慢
2. 代码含业务敏感信息，不宜外传
3. 网络不稳定时工具失效

替代方案采用双层架构：

```
LocalAnalyzer（规则匹配，全自动）  →  置信度 ~5，快速扫完全部
Claude Code（终端内深度分析）       →  置信度 7-9，人工/半自动做核心 API
```

整个系统在无网络、无 API key 环境下也能完整运行。

## 数据流架构

```
Scanner（正则扫描）
  ↓ 发现入口点（API / Cron / Entity）
Scheduler（SQLite 队列）
  ↓ 按优先级排序
ContextPreparer（核心组件）
  ↓ 提取方法体 + 追踪调用链 + 读 DB 结构 + 算代码质量
_contexts/*.json（上下文文件）
  ↓
┌────────────────────────────────────────────┐
│  分析引擎（二选一）                           │
│                                             │
│  [LocalAnalyzer] ──→ api/*.md（全自动）      │
│                                             │
│  [TaskCluster + ContextMerger]              │
│       ↓                                     │
│  _batch_requests/*.md                       │
│       ↓                                     │
│  Claude Code 读取并分析                     │
│       ↓                                     │
│  api/*.md（人工/半自动）                    │
└────────────────────────────────────────────┘
  ↓
KnowledgeGraph（关系图）+ SemanticSearch（搜索索引）
  ↓
GlobalSynthesizer（领域文档）
```

## 核心组件

### Scanner — 为什么用正则不用 AST？

原计划用 Java AST 解析器，实际使用正则。

真实代码里有注释掉的注解、未完成代码、混合中英文变量名，AST 遇到语法错误直接崩溃。正则"找到就找到，找不到就跳过"，更鲁棒。

扫描模式：
- `@GetMapping("/path")` → API 入口
- `@XxlJob("handler")` → 定时任务
- `@TableName("table")` → 实体类

### ContextPreparer — 最复杂的组件

承担"理解代码"的体力活，让分析器只需"推理业务"。

| 步骤 | 技术难点 |
|------|---------|
| 提取目标方法体 | Brace-aware 解析：处理字符串里的 `{`、行注释、块注释 |
| 智能截断 | 文件 >15K 字符时，只保留 imports + 类声明 + 字段 + 目标方法 |
| 调用链追踪 | 找到 `*Service*` / `*Mapper*` / `*Dao*` 调用，读取实现文件 |
| DB Schema 关联 | 正则发现表名 → 读 MySQL `INFORMATION_SCHEMA` |
| 代码质量计算 | 方法长度、魔法数字、`@Autowired` 数量、原生 SQL 插值 |

Brace-aware 方法提取要区分：
- `"字符串里有 { 括号"` — 不算
- `// 注释里有 { 括号` — 不算
- `/* 块注释 { 括号 */` — 不算
- `public void foo() { ... }` — 才算

### TaskCluster — 聚类分析的价值

逐个分析 1000 个 API，每个独立看代码，无法发现跨 API 的业务关联。

**聚类策略（三层）**：
1. **同 Controller 文件** → 强相关（如订单的 list/detail/create）
2. **同业务领域** → `order` / `payment` / `refund` / `member`
3. **共享 Service** → 两个 API 都调用 `OrderService.create()`

效果：分析一批 5 个相关 API 时，能发现"这 3 个 API 操作同一张表但状态判断逻辑不一致"、"A API 设置状态，B API 读取状态，构成状态机"。

### ContextMerger — 去重与关联

5 个 API 都调用 `OrderService`，如果每个上下文都包含完整 `OrderService` 代码，请求会极度冗长。

解决方案：提取"共享资源"（Service、Table、Enum），在批次请求中只出现一次。跨 API 关联示例：

```
API A 和 API B 共享服务: OrderService
API A 和 API C 操作同一张表: order_head
```

## 任务优先级设计

| 优先级 | 含义 |
|--------|------|
| 2 | 核心业务写操作（create / save / submit / pay） |
| 3 | 核心业务读/改操作 |
| 4 | 查询 / list 操作、定时任务 |
| 5 | 其他 |

Priority 1 预留给"阻塞其他任务的关键入口"。Priority 3 只有 215 个，是 ROI 最高的投入对象。

Entity 类型任务占 50%+（514 个实体类），但这些不需要深度分析，LocalAnalyzer 足够。

## 使用流程

### 第一阶段：快速全覆盖（2-3 小时）

```bash
python evolve.py --project wxapp-service \
  --project-path "C:\project\WxApp_Service" \
  --count 50 --mode local
```

产出：~976 张置信度 5 的骨架卡片。

### 第二阶段：核心深化（按优先级）

```bash
python evolve.py --project wxapp-service \
  --project-path "C:\project\WxApp_Service" \
  --count 10 --mode batch
```

`batch` 模式内部自动完成 prepare → cluster → merge。

### 第三阶段：知识整合

```bash
python -m engine.main synthesize --project-name wxapp-service
python evolve.py --project wxapp-service --contradiction-check
python evolve.py --project wxapp-service --feedback
```

## 踩坑记录

### `--prepare-only` 陷阱

错误操作：先 `--prepare-only --count 5`，再 `--mode batch --count 5`。

结果：第一批上下文准备好了但没被分析，batch 取了第二批新的。

正确做法：直接运行 `evolve.py --mode batch --count 5`，一步到位。

### `analyze_all_prepared` 遍历全部上下文

LocalAnalyzer 的 `analyze_all_prepared()` 每次遍历 `_contexts/` 下所有 JSON 文件。500+ 文件时会越来越慢，每个文件都要检查"是否已分析过"。

优化方向：只分析新准备的上下文，不要全量遍历。

### Integer 比较的 NPE 风险

```java
// 代码中的坏味道
custInfo.getCustType().equals(3)  // getCustType() 可能为 null，抛 NPE
```

分析时需要标记这种隐患，而不是只描述业务逻辑。

### 跨 API 状态判断不一致

同一个 `OrderStatusEnum`，API A 判断 `status == 1` 表示已创建，API B 判断 `status == 1` 表示待支付。单个 API 分析发现不了，只有 batch 聚类、对比多个 API 才能发现。这是 batch 模式的核心价值。

## 组件复杂度排序

按代码量和逻辑复杂度排序：

1. `context_preparer.py` — 最复杂（方法提取、调用链、DB schema、质量计算）
2. `task_cluster.py` — 聚类逻辑（三层分组、合并、拆分）
3. `context_merge.py` — 合并去重、交叉关联分析
4. `scanner.py` — 扫描器（正则匹配，逻辑简单但模式多）
5. `local_analyzer.py` — 规则分析器（模式匹配为主）
6. `knowledge_graph.py` — 图构建和查询
7. `task_scheduler.py` — SQLite CRUD
8. `db_connector.py` — MySQL 读取

## 扩展方向

| 方向 | 思路 |
|------|------|
| 支持更多语言 | 扫描器加 Go/Python 模式，brace-aware 逻辑通用 |
| 增量分析 | `incremental_evolver.py` 已支持 git diff 检测 |

| 代码重构建议 | 从知识图谱中发现重复逻辑、提取公共方法 |
| 测试用例生成 | 基于业务规则卡片自动生成边界测试 |

## 一句话总结

> **Scanner 发现入口，Scheduler 管理队列，ContextPreparer 做脏活累活（理解代码），Analyzer 做聪明活（推理业务），Graph + Search 让知识可查询，Synthesizer 让知识成体系。**

最关键的设计决策：**ContextPreparer 承担了"理解代码"的体力活，让 Analyzer 只需要"推理业务"**。这是整个系统能分析 1000+ API 的核心原因。
