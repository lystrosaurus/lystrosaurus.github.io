## 为什么需要统一用户体系？

在企业数字化进程中，我们往往面临这样的困境：

- 小程序有小程序的用户表，App 有 App 的用户表，同一个手机号在不同渠道是"不同的人"
- 员工在飞书是一个 ID，在企微是另一个 ID，在自建系统又是第三个 ID，数据无法打通
- 业务系统越来越多，用户数据散落各处，想要做统一画像、统一积分、统一权限，却发现连"这是同一个人"都无法确定

**用户体系设计的本质，是在多个异构系统之间建立"人的唯一性"。**

本文将从通用理论出发，结合两个真实业务场景，给出可落地的设计方案。

## 一、通用理论：身份标识的分层模型

### 1.1 三层身份模型

参考飞书开放平台的设计理念，我们可以将用户身份抽象为三个层次：

```
┌─────────────────────────────────────────────────────────────┐
│                     物理层（Physical）                        │
│  ┌───────────────────────────────────────────────────────┐  │
│  │              全局唯一用户（Global User）                │  │
│  │         唯一标识：global_id / uuid                     │  │
│  │    代表一个真实的"人"，系统内部使用，对外不可见         │  │
│  └───────────────────────────────────────────────────────┘  │
├─────────────────────────────────────────────────────────────┤
│                     业务层（Business）                       │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐         │
│  │  租户 A 身份  │  │  租户 B 身份  │  │  租户 C 身份  │         │
│  │  tenant_user │  │  tenant_user │  │  tenant_user │         │
│  │  (employee)  │  │  (employee)  │  │  (employee)  │         │
│  └─────────────┘  └─────────────┘  └─────────────┘         │
│  同一个人在不同企业/组织中拥有不同的业务身份               │
├─────────────────────────────────────────────────────────────┤
│                     应用层（Application）                    │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐             │
│  │小程序 │ │ 美团  │ │ 抖音  │ │ 有赞  │ │ App  │             │
│  │app_uid│ │app_uid│ │app_uid│ │app_uid│ │app_uid│             │
│  └──────┘ └──────┘ └──────┘ └──────┘ └──────┘             │
│  同一个用户在不同应用/渠道中拥有不同的应用身份             │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 各层标识符的设计原则

| 层级 | 标识符 | 生成规则 | 作用域 | 是否可见 |
|------|--------|----------|--------|----------|
| 物理层 | `global_id` | UUID / 雪花算法 | 全局唯一 | 内部使用 |
| 业务层 | `tenant_user_id` | 企业内自定义（工号/邮箱前缀） | 租户内唯一 | 对租户管理员可见 |
| 应用层 | `app_user_id` | 各渠道自生成 | 应用内唯一 | 对应用可见 |

**关键原则：**

- **上层标识符对下层透明**：应用层不需要知道 `global_id`，业务层不需要关心各渠道的 `app_user_id`
- **同层标识符不可跨域使用**：美团的 `app_user_id` 不能在抖音中使用（类似飞书的 `open_id` 不可跨应用使用）
- **通过映射关系实现跨层关联**：核心是一张映射表，将各层标识关联起来

### 1.3 账号聚合（Account Linking）

将多个渠道/系统的身份关联到同一个"人"的过程，称为**账号聚合**。常见策略：

```
                    ┌─────────────────┐
                    │   聚合策略       │
                    └────────┬────────┘
           ┌────────────────┼────────────────┐
           ▼                ▼                ▼
    ┌──────────┐    ┌──────────┐    ┌──────────────────┐
    │ 手机号聚合 │    │ Union ID │    │  运营手动合并     │
    │          │    │   聚合    │    │                  │
    │ 相同手机  │    │ 平台方提  │    │ 人工确认后绑定   │
    │ 号 = 同人 │    │ 供的统一  │    │ 适用于无法自动   │
    │          │    │ 标识      │    │ 关联的场景       │
    └──────────┘    └──────────┘    └──────────────────┘
     最常用          最准确          兜底方案
```

## 二、核心数据模型设计

### 2.1 核心表结构

```sql
-- 1. 全局用户表（物理层）
CREATE TABLE global_user (
    id              BIGINT PRIMARY KEY,          -- 全局唯一 ID
    uuid            VARCHAR(36) UNIQUE NOT NULL,  -- UUID，对外不可见
    created_at      TIMESTAMP DEFAULT NOW(),
    updated_at      TIMESTAMP DEFAULT NOW()
);

-- 2. 绑定因子表（用于账号聚合）
CREATE TABLE user_binding_factor (
    id              BIGINT PRIMARY KEY,
    global_user_id  BIGINT NOT NULL,             -- 关联全局用户
    factor_type     VARCHAR(20) NOT NULL,         -- phone / email / wechat_openid / ...
    factor_value    VARCHAR(255) NOT NULL,        -- 因子值
    is_verified     BOOLEAN DEFAULT FALSE,        -- 是否已验证
    UNIQUE(factor_type, factor_value)             -- 一个因子只能绑定一个用户
);

-- 3. 应用用户表（应用层）
CREATE TABLE app_user (
    id              BIGINT PRIMARY KEY,
    global_user_id  BIGINT NOT NULL,             -- 关联全局用户
    app_code        VARCHAR(50) NOT NULL,         -- 应用标识：miniapp / meituan / douyin / youzan
    app_user_id     VARCHAR(255) NOT NULL,        -- 渠道内的用户 ID
    app_union_id    VARCHAR(255),                 -- 渠道内的 Union ID（如有）
    nickname        VARCHAR(100),
    avatar_url      VARCHAR(500),
    extra           JSON,                         -- 渠道特有字段
    UNIQUE(app_code, app_user_id)
);

-- 4. 租户用户表（业务层，B 端场景）
CREATE TABLE tenant_user (
    id              BIGINT PRIMARY KEY,
    global_user_id  BIGINT NOT NULL,             -- 关联全局用户
    tenant_id       BIGINT NOT NULL,             -- 租户/企业 ID
    employee_id     VARCHAR(50) NOT NULL,         -- 企业内工号
    name            VARCHAR(100),
    status          VARCHAR(20) DEFAULT 'active', -- active / inactive / resigned
    UNIQUE(tenant_id, employee_id)
);
```

```

│──────────────│

       │
       ├──────────────────────┬──────────────────────┐

┌──────────────────┐  ┌──────────────┐  ┌──────────────────┐
│ user_binding_    │  │  app_user    │  │  tenant_user     │

    微信OpenID等
```

### 3.4 渠道适配层设计

每个渠道需要一个 Adapter，负责：

1. **登录适配**：将渠道登录态转换为统一的 `global_user_id`
2. **数据同步**：将渠道订单/行为数据同步到统一数据中心
3. **消息推送**：将统一消息分发到各渠道

```typescript
// 示例：渠道适配器接口
interface ChannelAdapter {
  // 渠道标识
  readonly channelCode: string;

  // 登录：渠道凭证 → 全局用户 ID
  login(credential: ChannelCredential): Promise<LoginResult>;

  // 同步：渠道用户信息 → 统一用户信息
  syncUserProfile(channelUserId: string): Promise<UserProfile>;

  // 推送：统一消息 → 渠道消息
  sendMessage(userId: string, message: UnifiedMessage): Promise<void>;
}

// 各渠道实现
class MiniAppAdapter implements ChannelAdapter { ... }
class MeituanAdapter implements ChannelAdapter { ... }
class DouyinAdapter implements ChannelAdapter { ... }
class YouzanAdapter implements ChannelAdapter { ... }
```

## 四、场景二：多系统 B 端员工体系

### 4.1 业务背景

一家中大型企业同时使用以下系统：

| 系统 | 用途 | 员工标识特点 |

| 北森 | HR 系统（招聘/考勤/薪酬） | 北森员工 ID |
| 飞书 | 办公协作（IM/文档/日历） | `open_id` / `user_id` / `union_id` |
| 企微 | 客户管理/内部沟通 | 企微 `userid` |
| 自建系统 | OA/ERP/CRM 等 | 工号 / 自定义 ID |

**核心诉求：** 员工入离职时，各系统身份同步开通/注销；统一组织架构；跨系统单点登录。

### 4.3 数据模型：身份映射表

```sql
-- 员工主数据（以 HR 系统为主数据源）
CREATE TABLE employee (
    id              BIGINT PRIMARY KEY,
    tenant_id       BIGINT NOT NULL,
    employee_no     VARCHAR(50) NOT NULL,          -- 工号
    name            VARCHAR(100) NOT NULL,
    email           VARCHAR(255),
    phone           VARCHAR(20),
    department_id   BIGINT,
    position        VARCHAR(100),
    status          VARCHAR(20) DEFAULT 'active',  -- active / onboarding / resigned
    hire_date       DATE,
    resign_date     DATE,
    UNIQUE(tenant_id, employee_no)
);

-- 跨系统身份映射
CREATE TABLE employee_identity_mapping (
    id              BIGINT PRIMARY KEY,
    employee_id     BIGINT NOT NULL,               -- 关联员工主数据
    system_code     VARCHAR(50) NOT NULL,           -- beisen / feishu / wecom / oa / erp
    system_user_id  VARCHAR(255) NOT NULL,          -- 该系统中的用户 ID
    system_union_id VARCHAR(255),                   -- 飞书 union_id 等
    display_name    VARCHAR(100),                   -- 该系统中的显示名
    synced_at       TIMESTAMP,                      -- 最后同步时间
    UNIQUE(system_code, system_user_id)
);
```

### 4.7 各系统对接要点

**北森（HR 主数据源）**

- 通过北森 OpenAPI 同步组织架构和员工信息
- 监听入职/离职/调岗事件（Webhook）
- 作为员工主数据的权威来源

**飞书**

- 使用 `user_id`（企业内身份）进行 API 调用
- 通过 `union_id` 关联同一服务商下的多应用
- 通过通讯录 API 同步组织架构

**企微**

- 使用企微 `userid` 进行 API 调用
- 通过通讯录同步接口维护组织架构
- 支持 SSO 登录（OAuth2）

**自建系统**

- 直连数据库同步员工信息
- 实现 SSO 对接（SAML / OAuth2 / CAS）
- 权限体系对接（RBAC）

## 五、关键设计决策

### 5.1 主数据源的选择

```
┌─────────────────────────────────────────────────────┐
│  C 端场景                                           │
│                                                     │
│  主数据源 = 统一用户中心                             │
│  各渠道数据 → 同步到用户中心                         │
│  用户中心 = 唯一权威来源                             │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│  B 端场景                                           │
│                                                     │
│  主数据源 = HR 系统（北森）                          │
│  HR 数据 → 同步到统一身份平台                        │
│  统一身份平台 → 同步到各子系统                       │
│  员工信息变更必须从 HR 系统发起                      │
└─────────────────────────────────────────────────────┘
```

### 5.2 数据一致性保障

| 策略 | 适用场景 | 实现方式 |
|------|----------|----------|
| 实时同步 | 对时效性要求高 | Webhook + 消息队列 |
| 准实时同步 | 允许秒级延迟 | 变更事件 + 异步任务 |
| 定时对账 | 兜底保障 | 每日全量比对 + 差异修复 |

## 六、总结

| 维度 | C 端（多渠道用户） | B 端（多系统员工） |
|------|-------------------|-------------------|
| 核心问题 | 同一个人在不同渠道是不同的人 | 同一个员工在不同系统是不同的人 |
| 聚合方式 | 手机号 / Union ID / Open ID | 工号 / 邮箱 / HR 主数据 |
| 主数据源 | 统一用户中心 | HR 系统 |
| 同步方向 | 渠道 → 用户中心 | HR → 身份平台 → 各系统 |
| 核心表 | global_user + app_user | employee + identity_mapping |
| 关键能力 | 账号聚合、统一会员 | 生命周期管理、SSO、组织同步 |

**设计用户体系的核心原则：**

1. **唯一性**：一个"人"在系统中有且仅有一个全局标识
2. **隔离性**：不同渠道/系统的身份互不干扰
3. **可关联**：通过映射关系实现跨系统打通
4. **可追溯**：任何身份变更都有完整审计日志
5. **可扩展**：新渠道/新系统接入时，只需新增适配器和映射记录
